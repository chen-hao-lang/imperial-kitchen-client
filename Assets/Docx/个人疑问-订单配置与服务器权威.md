# 个人疑问：订单配置与服务器权威

> 记录时间：2026-08-12
> 相关代码：`RecipeRegistry.cs`（服务端）、`KitchenObjectRegistry.cs`（客户端）、`ServerDeliveryManager.cs`
> 相关文档：`联机.md` 第十步「服务器权威的订单同步」

---

## 一、原始疑问（未优化）

> 当前的菜单在服务器上是写死的，如果客户端进行更新，那么服务器也得进行同步更新。如果客户端存在不同的场景，每个场景可能能做不同的菜，那么服务端也得针对每个场景去写好每个场景对应的配菜。这样子也太麻烦了吧？为何不像类 `KitchenObjectRegistry.cs` 一样，在连接服务器后，上报服务器器，服务器再进行注册。如果这样子做，那还是服务端权威吗？

---

## 二、优化后的问题

### Q1：服务端配方"写死"的维护成本

当前服务端 `RecipeRegistry` 将配方表直接写死在代码里。若客户端内容更新（新增/修改菜品），服务端必须同步改代码并重新发布；若客户端存在多个场景、每个场景可制作不同的菜品，服务端还要为每个场景分别维护一套配方配置。这种"内容写死"的方案维护成本是否过高？有没有更优雅的配置分发 / 管理方案（如服务端配置文件、客户端上报、版本握手等）？

### Q2：客户端上报内容是否会破坏"服务端权威"

参照 `KitchenObjectRegistry` 的思路（连接后由客户端上报、服务端再注册使用），是否可以让客户端在连接后上报配方表、由服务端注册后再用于订单逻辑？这样做之后，订单生成、交付校验、计分仍由服务端执行，**是否还算"服务端权威"**？"客户端上报内容"与"服务端权威"的边界到底在哪里？

### Q3：客户端上报内容的可信度与反作弊

如果服务端接受客户端上报的配方，恶意或被篡改的客户端是否可能上报"极易完成"的配方（例如单一配料即可匹配所有订单），从而刷分？在协作类 / 学习类项目与竞技类项目之间，这一风险应如何权衡？服务端应如何校验与约束客户端上报的内容？

### Q4：内容版本一致性

客户端与服务端内容不一致时（例如客户端已更新配方、服务端仍是旧配方），如何检测与处理？是否需要引入内容版本号 / 哈希握手，版本不匹配时拒绝连接或提示更新？

---

## 三、参考解答

### 1. 先分清"权威"的两层含义

| 层面 | 含义 | 例子 | 必须由谁决定 |
|------|------|------|------|
| **状态权威（State Authority）** | 决定游戏"当前是什么"：订单何时出现、交付是否成功、分数是多少 | 刷单计时器、交付校验结果、`ScoreUpdate` | **必须服务端**（反作弊 + 多端一致性） |
| **内容权威（Content Authority）** | 决定游戏"有哪些内容"：物品定义、配方组成、操作台类型 | `RecipeRegistry` 里的配方表、`KitchenObjectRegistry` | 视方案而定，可以放服务端也可以由客户端提供 |

当前项目把**两层权威都放在了服务端**（配方表写死在 `RecipeRegistry`），这是最"正统"但也最笨重的做法。

### 2. 回答 Q2：客户端上报内容 ≠ 放弃服务端权威

**只要订单的"裁决动作"仍在服务端，就仍然是服务端权威。** 客户端上报配方表，本质上只是向服务端"提供一份静态数据"，服务端收到后仍然：

- 用**自己的定时器**决定刷单时机与顺序；
- 用**服务端登记的配方** + **服务端维护的 `ServerPlate.Ingredients`** 做交付校验；
- 在**服务端**加分并广播 `ScoreUpdate`。

所以"内容由客户端提供"与"状态由服务端裁决"可以并存。权威的边界一句话概括：

> **内容可以来自任何一方，但"结果"只能由服务端拍板。**

### 3. 回答 Q3：信任边界与反作弊

客户端上报内容有一个真实的代价：**服务端在"内容"上信任了客户端**。被篡改的客户端理论上可以上报"任意配料都能匹配"的配方，导致交付必成功、分数被刷。

但这个风险是否值得担心，取决于项目类型：

| 项目类型 | 对内容可信度的要求 | 结论 |
|----------|--------------------|------|
| 协作 / 学习项目（本项目） | 低——玩家没有作弊动机，积分无实际意义 | **可以接受客户端上报内容** |
| 竞技 / 计费项目 | 高——内容必须服务端权威 | 必须用"服务端配置文件"或"白名单校验" |

即便采用客户端上报，服务端也应做**防御性校验**（低成本、高收益）：

- 只接受合法索引：配料索引必须落在 `KitchenObjectRegistry` 有效区间（`0..Count-1`）内，拒绝 `-1` / 越界；
- 约束结构：每条配方配料数量上限（如 ≤ 6）、配方总数上限（如 ≤ 32）、去重；
- 可选：对已知内容做哈希校验，只接受与官方版本匹配的内容。

### 4. 回答 Q1：配置分发的方案对比

| 方案 | 做法 | 内容权威 | 维护成本 | 适用场景 |
|------|------|----------|----------|----------|
| **A. 服务端写死（当前）** | 配方表硬编码在 `RecipeRegistry` | 服务端 | 高（每次改内容都要同步改代码 + 发布） | 内容极少变化、竞技项目 |
| **B. 服务端配置文件** | 服务端从 JSON / 数据库加载配方，每个场景一份配置 | 服务端 | 中（改配置无需重编译，但仍需部署到服务器） | 多场景、内容由服务端掌控的常规做法 |
| **C. 客户端上报 + 服务端校验** | 连接后上报配方，服务端校验并注册 | 状态服务端 / 内容半信任 | 低（客户端更新即生效，服务端零改动） | 协作 / 学习项目、内容频繁变化 |
| **D. 混合（场景 ID + 服务端配置）** | 客户端只上报"我在哪个场景"，服务端按场景 ID 取自己的配置 | 服务端 | 中 | 多场景但内容仍由服务端掌控 |
| **E. 内容版本握手** | 客户端上报内容版本 / 哈希，服务端比对，不匹配则提示/拒绝 | 服务端 | 低 | 防止"客户端更新了、服务端没更新"的错配 |

> 关键洞察：**A 与 C 不是二选一的对立，而是"内容放哪"的取舍。** 多场景问题用方案 B / D 解决更"正统"；"客户端更新服务端不用动"用方案 C 最省事；"检测内容不一致"用方案 E。

### 5. 对本项目的具体建议

本项目是**协作 / 学习项目**，且项目里已有先例——操作台类型映射就是客户端连接后通过 `C2S_CounterRegister` 上报、服务端注册的。因此**方案 C（客户端上报配方 + 服务端校验）完全可行**，且风格统一。

落地思路（保持现有协议基本不变）：

```
新增 C2S_RegisterRecipes（客户端 → 服务端）
  body = recipeCount(int) + [ingredientCount(int) + [ingredientIndex(int)]*N] * recipeCount

服务端 HandleRegisterRecipes：
  ├─ 校验每条配料的索引合法（0..KitchenObjectRegistry.Count-1）、数量上限、去重
  ├─ 合法 → 替换当前"已注册配方表"（第一个上报者优先，类似 C2S_CounterRegister）
  └─ 不合法 → 拒绝并告警

订单逻辑（ServerDeliveryManager）：
  ├─ 刷单：从"已注册配方表"随机选 index 广播 RecipeSpawned(index)
  ├─ 校验：用注册表 Matches() + ServerPlate.Ingredients（不变）
  └─ 计分 / 广播：不变
```

要点：

- **`recipeIndex` 的映射一致性**：所有客户端来自同一份游戏构建，上报内容相同，因此服务端广播的 `recipeIndex` 在所有客户端上解析出的配方一致（客户端仍用本地 `RecipeListSO` 做展示）。若有玩家用旧版本客户端连入，其本地配方表顺序可能不同——这正是 Q4 中"版本握手"要防的问题。
- **多场景支持**：客户端在切换场景 / 关卡时重新上报当前场景的配方表即可，服务端按"最新上报"替换注册表，无需为每个场景写死配置。
- **交付校验仍然服务端权威**：校验用的是服务端 `ServerPlate.Ingredients` 状态，不是客户端上报的"本次交付内容"，这一点与现在完全一致。

### 6. 结论（一句话版）

> **"服务端权威"管的是"结果"，不是"内容"。** 内容写死最正统但最笨重；客户端上报内容 + 服务端校验，可以让客户端更新服务端零改动、天然支持多场景，且订单裁决仍在服务端——对本项目是完全可行的方案，只需加上防御性校验和内容版本握手即可。
