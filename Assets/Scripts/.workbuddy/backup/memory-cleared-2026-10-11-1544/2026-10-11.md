## 运行时报错定位：HTTP 被 Player Settings 拦死 → 连锁引发「清单缺失」

用户切成 `HostPlayMode` 后跑起来，报 **2 警告 + 2 报错**。四条日志**只有一个根因**，其余全是连锁。

### 根因（P0-10）：`insecureHttpOption: 0` 把 HTTP 下载禁掉了

- 铁证：`ProjectSettings/ProjectSettings.asset:953` = `insecureHttpOption: 0`（`InsecureHttpOption.NotAllowed`，Unity 2020.2 起的**默认值**）。
- 而本项目 CDN 是 `http://106.52.92.221/CDN/PC/v1.0`（公网 IP、无证书、`CdnConfig.UseHttps = false`）。
- 于是 `UnityWebRequest` 在**创建请求**阶段就被拒，报文根本没发出去。两条报错原文：
  - `Non-secure network connections disabled in Player Settings`（栈顶指向 `UnityWebRequestBase.cs:143`）
  - `[YooAssetsLoad] Request package version failed: [UnityWebRequestText] Failed to create web request: Insecure connection not allowed.`
- **排查关键（写进指南 §6.7）**：这是**瞬间**失败，且 nginx `access.log` 里**一条记录都没有**。
  - 🧠 **判断口诀：瞬间报 "Insecure" = 被 Player Settings 拦了；卡住 21 秒报 "timed out" = 被安全组拦了。** 两者都不要去重启 nginx。
  - 两者都是**静默失败**：文档缺这条时极容易误判成"服务器不通/证书问题"。

### 连锁（P0-11）：没有激活的清单 → `YooPackageInvalidException`

### 为什么回退必须「整包换模式」而不是「退回内置清单」

`OfflinePlayMode` 的文件系统**就是** `BuiltinFileSystem`：版本读 `StreamingAssets/yoo/{包名}/{包名}.version`，清单读同目录的 `{包名}_{版本}.bytes`，**天生不需要网络**。
所以正确做法是销毁包（`DestroyPackage` 会同时清 `YooAssets` 注册表与 `YooAssetsLoad._packageCache`）后**以 `OfflinePlayMode` 重跑同一套流程**。

两层回退已落地且同构：
1. `UIManager.InitUIConfig` —— 保证"CDN 挂了也能进主菜单"；
2. `PackagePatchStep.Run` —— 保证其余 4 个包也不会卡死启动。

> 定位：回退是**降级保命**（不卡启动页），**不是"离线也能玩"**（本游戏要 TCP 连服务器，没网进不了对局）。回退成功会留警告日志，看到它就意味着"热更没生效，正在用内置资源跑"。

### 关键设计决策（都写了注释说明原因）

1. **用 `sftp -b <批处理文件>`，不用 `scp`**：
   - `scp -r localDir host:remoteDir` 在 remoteDir **已存在**时会把源目录名再套一层（变成 `remoteDir/v1.0/...`）—— 经典坑；
   - 要用 `scp` 规避就得先 `rm -rf` 远端，不想在脚本里放这个；
   - 批处理文件还有个额外好处：**可以打开看、可以复制到命令行手动重跑**，排查时非常有用。
2. **`-o BatchMode=yes` 是必需的**：密钥不通时立即报错退出，而不是挂着等输入密码 —— 编辑器里没有终端，进入交互式提问的表现就是"Unity 假死"。
3. **`lcd` 用正斜杠**（`F:/...`），避免反斜杠被 sftp 当转义字符；同时把 `ProcessStartInfo.WorkingDirectory` 也设成暂存目录做双保险。
4. **外部进程输出用 `OutputDataReceived` 事件异步收集 + 轮询，不用 `ReadToEnd()`**：同步读会阻塞主线程导致界面卡死，且子进程输出写满管道缓冲区时会**死锁**。回调跑在后台线程，所以 `List` 访问加了 `lock`。
5. **进度条用 `EditorUtility.DisplayCancelableProgressBar`**，按 sftp 输出里 "Uploading" 行数计入，显示 `已上传 n/总数`。
6. **增量判断依据**：YooAsset 的 bundle 文件名就是内容哈希 → **同名 + 同大小 == 同一份文件**。收集时比对暂存目录已存在的同名文件，只把"新出现/大小不同"的记为变化，上传时逐个 `put`。日常改一张贴图通常只有 1~2 个 bundle 变化。
7. **暂存目录 `CdnUpload/` 不再每次清空**（改了旧 `prepare-cdn.ps1` 的清空语义）—— 它现在长期扮演"远端 CDN 目录的本地镜像"，清了就没有增量比对基准了。
8. **`CdnDeployConfig` 与 `CdnConfig` 分离**：前者是"开发机传到哪"（SSH 账号/私钥/远端根目录），后者是"客户端运行时去哪下"。`SshHost` 直接取 `CdnConfig.PrimaryHost`（两者都是 `const`，可以互相引用）避免写歪；平台目录映射单独实现但注释要求与 `CdnConfig.PlatformFolder` 保持一致。
9. **避免 `using System.Diagnostics;` 与 `UnityEngine.Debug` 的 CS0104 二义性**：文件里用 `using Debug = UnityEngine.Debug;` 别名钉死，并在顶部注释说明这个 Unity 常见坑。

### 开工前的关键发现（**比工具本身更重要**）：固定版本号会让热更永久静默失效

原本打算只写上传工具，勘查时发现 `Bundles/StandaloneWindows64/` 下 5 个包的版本目录**全是固定值 `v1.0`**，这会让热更完全失效。完整证据链（三处代码实证）：

| 事实 | 出处 |
| --- | --- |
| 沙盒清单缓存文件名**含版本号**：`GetManifestBinaryFileName(PackageName, packageVersion)` | `SandboxFileSystem.cs:419` |
| `DownloadPackageManifestOperation` 有 `CheckExists`：本地已有该文件就 **`SetResult()` 直接复用，不再下载** | `DownloadPackageManifestOperation.cs` |
| `ClearPackageCache` 只清 **bundle**，**不动**清单文件（清单要靠单独的 `ClearAllCacheManifest`） | `SFSClearCacheOperation` → `BundleCache.ClearCacheAsync` |

**推论：版本号不变 → 缓存路径不变 → 客户端永远复用旧清单 → 改了资源重新上传也毫无效果，且不报任何错。**

> 这条把记忆里原来标为 `P2-1（待修隐患：回滚手段失效）` 的问题**升级为硬阻塞**——它不是"回滚不方便"，而是"热更根本不会生效"。
> 好消息：这也解释了为什么之前"改一次版本号重建上传"才能看到下载行为。

同类补充事实（`LoadPackageManifestOperation.cs:55`）：同一进程内若 `ActiveManifest.PackageVersion == 请求版本`，也会直接 `SetResult()` 跳过重载 —— 但这是次要的，跨进程启动时 `ActiveManifest` 为 null。

### 几个刻意的设计决策（都值得保留）

1. **增量判定用「远端清单 diff」，不用本地状态文件。** 先一次 `ssh` 完成 `mkdir -p && ls -1`，再与本地文件集比对。好处：天然幂等、失败后可重跑续传、换机器无需迁移任何状态。
2. **`{包名}.version` 强制重传。** 它**名字固定、内容每次构建都变**，而客户端正是靠它判断有没有新版本；其余文件名字里带内容哈希或版本号，"远端同名"即"内容相同"。
3. **`{包名}.version` 的存在性依赖 `CheckExists` 的语义**，上面第 2 条与它配套。
4. **sftp 批处理不加 `-` 前缀**（即"出错继续"），宁可单文件失败就中止也不静默跳过 —— 因为重跑成本极低。
5. **`ssh` 用 `-p`、`sftp` 用 `-P`**（大小写不同，极易写错）。
6. **`BatchMode=yes`**：认证失败直接返回非 0，绝不让进程卡在密码提示上把 Unity 挂死。
7. **单包构建后自动收集 + 询问是否上传**，把"改了 UI 想赶紧看效果"这条路径压到最短。

## 🔴 P0-13 建档：固定包版本号让热更整体静默失效（本次实测确认「已中招」）

### 起因
撰写指南 §6.8 时，需要把"版本号必须每次不同"从断言升级为实证。检查本机实况时发现：
**项目当前正处于这个坑里，不是理论风险。**

### 实测证据（2026-10-11）
| 证据 | 实测值 |
| --- | --- |
| `Bundles/StandaloneWindows64/{UI,GameRoomScene,PlayerPrefab,GameScene}/` 版本目录名 | 全部只有 **`v1.0`** |
| CDN 暂存 `CdnUpload/PC/v1.0/` 下 5 个 `.version` 文件内容 | 全部是字符串 **`v1.0`** |
| 客户端沙盒 `Library/yoo/{包名}/ManifestFiles/` | `UI_v1.0.bytes` / `UI_v1.0.hash`，**版本号写死在文件名里** |

### 三条代码事实（本仓源码，已逐条读到）
1. `SandboxFileSystem.cs:419-423` `GetCachePackageManifestFilePath(packageVersion)` → `PathUtility.Combine(_cacheManifestFilesRoot, GetManifestBinaryFileName(PackageName, packageVersion))`。**版本号是缓存路径的一部分**（`_cacheManifestFilesRoot` = `{沙盒}/{包名}/ManifestFiles`，见 `:327`）。
2. `DownloadPackageManifestOperation.cs:45-56` `CheckExists` 分支**只判断 `File.Exists(_savePath)`**：存在就 `SetResult()` 直接成功返回，**不请求远端、不比对内容、不看时间戳**。
3. `ClearPackageCache`（→ `SFSClearCacheOperation` → `BundleCache.ClearCacheAsync`）**只清 bundle，不动清单**；清单需单独 `ClearAllCacheManifest`。

### 为什么它是"静默失效"
```
版本号固定 v1.0 → 缓存路径恒定 → CheckExists 命中 → 永不下载远端清单
→ 客户端按旧清单判定 → 旧清单里 bundle 名（内容哈希）没变 → 判定"无需更新"
→ 上传 1.2 GB 新资源，客户端一个字节都不下，且不抛异常、不打警告
```
附加一条：`LoadPackageManifestOperation.cs:55` 附近——同一次运行内 `ActiveManifest.PackageVersion == requestedVersion` 时**跳过重载**，
所以"改完重启 Play 验证"在版本号不变时**永远只能看到假象**。

### 修复方式（工具已具备，需用户换一次构建方式）
- `CdnDeploySettings.CreatePackageVersion` 自动生成 `yyyy-MM-dd-HHmm`（同分钟碰撞追加 `-2`/`-3`）；
- `CdnDeploySettings.IsFixedStyleVersion` 正则 `^v\d+(\.\d+)*$` 识别固定风格；
- `CdnStagingCollector.Collect` 命中固定风格 → **硬拦截报错中止**；
- 因此**只要走菜单 `KitchenChaos/热更发布/` 就踩不到**。危险动作只剩"在 YooAsset 构建窗口手填固定 Package Version"。

### 一个重要的概念区分（写进 §6.8，避免混淆）
| # | 名字 | 例子 | 能否固定 |
| - | --- | --- | --- |
| ① | App 版本 `CdnConfig.AppVersion` | `v1.0` | ✅ 可以（只是 CDN 目录名） |
| ② | 包版本 `PackageVersion` | `2026-10-11-1509` | 🔴 **必须每次不同** |
| ③ | 清单文件名 | `UI_2026-10-11-1509.bytes` | 由 ② 派生 |

①固定无害，②固定致命——两者常被写成同一个字符串（本项目现在就是），所以极难察觉。
